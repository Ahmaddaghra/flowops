# Phase 4 QA traceability

This matrix maps the implemented Stage 4A–4E requirements to existing tests and the Stage 4F QA artifacts. It is a coverage map, not a claim that every layer exercises every requirement. A dash means that layer does not own the behavior; explicit limits are retained where an ordinary HTTP/manual workflow cannot prove a database guarantee.

The approved Stage 4E baseline was **110 unit / 133 PostgreSQL / 204 frontend tests**. Stage 4F's material negative-path audit adds two HTTP invalid-status cases and strengthens twelve existing expectedVersion cases without adding duplicate tests. Current automated totals are **110 unit / 135 PostgreSQL / 204 frontend**, with frontend coverage unchanged. All **49 collection requests and 123 named Postman assertions** passed against the real API/disposable PostgreSQL database using an equivalent script runner. Official collection v2.1 schema/syntax, 51 embedded scripts, and 25 placeholder variables were validated. No native Postman CLI/Newman execution or GUI import is claimed. Collection execution and secret-review outcomes are recorded in [postman-guide.md](postman-guide.md) and [the Phase 4 checkpoint](../phases/phase-4-auth-collaboration-qa.md).

The [manual suite](manual-test-cases.md) has **28 designed cases**; none is relabelled as a newly executed manual case merely because a related automated/API/browser check passed. Historical 4C/4D/4E browser evidence is identified individually. The [six bug reports](bug-reports.md) cite actual pre-fix revisions, fixes, and retained regressions. No Stage 4G delivery, push, PR, or Phase 5 work is claimed.

## Negative automated-test audit

No frontend gap warranted new tests. Existing coverage includes:

- Login failure/retry: `AuthUI` generic failure and connection-failure cases.
- Current protected `401`, stale-session `401`, and concurrent invalidation: `Client`, `Provider`, and `CommentClient` use actual central-client/session code.
- `403` retention: central client plus status/form/assignment/comment local-error tests.
- Stale edit: `Detail` frozen expectedVersion, retained draft/conflict, no auto-retry; `Form` conflict presentation.
- Assignment `403`/`409`: `AssignmentUI` visible error, preserved state, explicit refresh, and pending duplicate guard; detail API/version-chain regressions.
- Failed comments and route races: `CommentsUI` field/server/generic failure retention, old GET/POST/retry responses, late GET merging, and `Detail` preventing wrong-route Activity refresh.

The backend audit identified **test-evidence gaps**, not new product defects:

1. The previous `WorkPG.InvalidExpectedVersion_ReturnsValidationProblem` used an assignment body containing fields rejected by the strict assignment DTO. A `400` could therefore pass for the wrong reason. Stage 4F supplies route-specific bodies and requires an expectedVersion-specific validation error for missing, zero, negative, and malformed values on edit/status/assign. Twelve existing parameter cases are strengthened; the count does not increase.
2. Domain tests rejected invalid status enums, but HTTP status-body validation had no dedicated mutation-free assertion. `WorkPG.InvalidStatus_ReturnsFieldValidationProblem_WithoutMutationOrActivity` adds two cases (`Unknown`, `999`), asserting `400`, field-specific safe Problem Details, and unchanged item/activity.

Existing PostgreSQL cases already cover malformed/expired JWTs, anonymous requests, unrelated Member edit/status, unauthorized assignment/reassignment/unassignment, stale client versions, invalid transitions, comment validation, spoof fields, and transaction rollback. They remain the authoritative negative persistence evidence; representative Postman requests add reproducibility without duplicating every parameter combination.

## Evidence limits

Historical browser checks cover local Chromium at desktop/mobile sizes and retain their original scope. Deliberate response interception is labelled separately from real server responses. A designed manual case is not passed by association with a unit test. An equivalent collection script, if used instead of a Postman CLI/Newman runner, must be named accurately in the execution record. Postman environment templates retain placeholders only; runtime exports, credentials, bearer values, and signing keys are not QA deliverables.

Comments follow the existing authenticated read policy, including legacy items. Account deactivation after token issuance retains the existing valid-claims behavior until expiry for work item reads/comments; login and `/auth/me` perform active-account checks. There is no refresh token, server logout/revocation service, comment expectedVersion, comment editing/deletion, or later-phase feature in these QA artifacts.
